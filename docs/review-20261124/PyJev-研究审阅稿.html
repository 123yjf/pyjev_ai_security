面向企业 AI 网关的轻量事后审计：指令语境、复核误差与 CPU 开销

研究问题。 网关已经把回答发给客户。此时有一段获准审计的文字：哪些值得交给审核员？哪些只是在讨论某条指令？我们研究的是事后分拣，不是在响应途中阻断请求，也不是根据文字推断一个人是否实施了攻击。

主要发现。 在同一台 Apple M4、同一批 924 条公开短文本上，Scope-1 每条审计的中位耗时为 0.276 毫秒，CPU 版专用分类器 HikmaAI 为 16.617 毫秒。但在其中 450 条带注入的工具回包上，前者漏了 413 条，后者漏了 71 条。一个系统确实可以便宜到适合本地逐条分析，却仍然不适合决定哪些回包可以不再检查。以下分别检验这两个命题。

1　为什么要分开判断“写了什么”和“要谁去做”

比较两句只改变外层要求的话：

输入给同一个检测器的文字 Scope-1 判定的意图 是否建议送审
请解释引文“给会议记录编号”的语气。 mention：讨论引文 否
请按引文中的要求去做：“给会议记录编号”。 act：要求办理 否

引文里的动作完全相同。只看到“编号”，无法区分谁要做什么；即便判断出用户确实要助手办理，“编号”仍是正常工作。还有第三种情况：工单记载一封外部邮件曾要求助手把内部资料交给陌生人。这里值得复核的是被记载的事件，不能归罪于写工单的人。三个例子均为自编，用来解释接口，不作为准确率证据。可运行输入、两种版本的完整返回

这决定了输入输出契约：一次只读一段文字；分开返回可疑线索、文字意图、复核建议。程序没有工具执行回执、用户授权凭证或可信消息角色，所以不输出“攻击成功”“用户越权”“模型为假”。输出也不调用工具、不写审计日志、不发邮件、不改计费。若未来接入网关，应由调用方在响应完成后，用独立队列传入最小必要文本；队列不是这个库已实现的功能。

2　为什么从词表走到上下文，而不是只增加规则

第一步是把可疑表述识别为复核线索。v0.1.0 保留双语词表提供的特征，再用训练所得的稀疏线性权重为词和短字符片段组合打分。推断时读取冻结的数值参数；它既不是按关键字逐字封禁，也不是调用大模型生成解释。第二个分类任务单独看外层表述：先区分引文与外层要求，再判断是在解释、要求办理还是无法确定。词表和学习权重解决“像不像可疑表述”；语境层解决“这是谁的话”。

3　区分语境之后，在没用于本轮改程序的材料上是否更可靠？

先冻结 v0.1.0、Scope-1 与 HikmaAI 的版本及阈值（0.5），再固定输入和参考标签、生成预测，最后合并答案计分。三者看到的是同一段未带答案的文字。主分析有 914 条：450 条注入工具回包与 464 条正常材料；另有 10 条历史事件描述，避免把“认出事故报道”错算为“抓到正在发生的注入”。实测材料是公开基准与文档，不是客户日志，也无法证明第三方模型预训练时从未见过它们。固定来源 · 预先确定的计分与取样方法

图 1　同一检测器的错误随文本类型改变。 阳性组读漏报，正常组读误报，两者均是越少越好。每格的分母不同，不能将五类误差简单取平均。

在 450 条注入回包上，原版、候选、HikmaAI 分别漏 428、413、71 条；在 401 条正常工具任务上，则分别误报 4、4、36 条。候选减少了 15 次漏报，没有丢掉原版在这批回包中检出的 22 条。它的误报较少，不能反推检测能力更强：它本来就更少报警。450 条阳性来自 15 个模板各 30 条，不是 450 个独立企业或独立场景。图 1 完整数表与模板级核查

讨论与引用也不可合并后就宣布胜负。在 27 条正常讨论中，候选误报 16 条，HikmaAI 19 条；在 21 条正常引用中，候选误报 10 条，HikmaAI 5 条。换到另一种文体，两者的相对表现就反过来了。

图 2　“没有报警”和“理解了引用”是两个指标。 在 48 条有人工意图标注的讨论与引用里，候选明确答对 18 条；原版是 0 条。候选其余 30 条中，26 条保留不确定，4 条被错读为要求执行。HikmaAI 不输出这个三分类标签，不能拿它的注入分数充当意图答案。

历史回归决定是否晋升。候选保留了指定的 481/481 条历史复核命中，旧 Agent 题的漏报从 147/153 降至 140/153。但 320 条旧办公意图题的正确数由 280 降到 250：40 条原本正确的判断被改错，只找回 10 条。注入命中得以保留，不等于意图能力没有退步。Scope-1 不替换 v0.1.0。 原版 PyBot 是对话接口对照，不输出这套安全标签；不将它列为“召回率为零”的分类器。逐项回归证据 · PyBot 对照

4　“轻量”能不能用墙钟时间和资源用量证明？

检测效果并不证明计算成本。为此只改变检测器，在同一台 Apple M4（10 个逻辑 CPU、16 GiB 内存），macOS 26.2 arm64，CPython 3.11.5 上重放相同的 924 条文本。三种系统均只用 CPU，逐条、串行、批大小为 1；HikmaAI 使用量化 ONNX，包含分词及分类推断，算子内 2 线程、算子间 1 线程，不包含网络下载。每个系统用 3 个新进程各跑一遍，轮换先后顺序；每进程先做 12 次相同预热，不计入延迟。这是 924 条不同材料，不是 2,772 条新的质量测试题。

表 2　在相同输入上测出的资源开销。 p50 表示一半输入不超过该耗时，p95 表示 95% 不超过；CPU 时间累计进程所有线程，因而可高于墙钟耗时。内存是包含解释器和模型在内的进程峰值，不是模型文件大小。

HikmaAI 的单条中位耗时约为候选的 60.1 倍，进程峰值内存约为 39.4 倍。两种 PyJev 共用的推断参数文件为 1,407,295 字节；HikmaAI 的 ONNX 与分词器文件合计 354,805,446 字节。文件大小不含代码、解释器或依赖，不能用来替代 RSS。审计速度是有证据的优势；结合图 1，不能把它写成“以更小算力达到相同检出效果”。逐轮原始汇总、p99、装载时间和串行速率 · 计时代码

边界：这些是短文本（中位 99、p95 为 263、最长 822 个 Unicode 字符），不足以给 32,768 字符的接口上限估速。未测生产流量、并发、队列、端到端 TTFT、GPU、能耗或人工审核工时。不同硬件和文本长度应重测，不把 60.1 倍写成产品承诺。

5　结论、使用决策与下一项实验

PyJev 当前最有证据支持的用途是：无需把正文再发给第三方，便能以较小的本地 CPU 和内存开销，给每段文本附上一条可读的复核理由类别。 对企业有价值的分界不是“能不能识别所有攻击”，而是“哪些判断可低成本提供，哪些必须保留给专用检测器或人”。适合离线抽样与审核试验，不适合作执行许可、客户定责或唯一防线。尤其不要用“PyJev 阴性”作为跳过工具回包独立检查的条件；这会排除本次漏掉的 413 条。也不能把两种检测器的检出数相加，宣称已验证组合系统。

下一项值得做的实验不是再报一个总准确率：在获授权、去标识并由多人独立标注的真实工作流中，按“外部工具回包、正常任务、内部安全讨论”分层，配对比较每千条误送审数、漏过的阳性数、人工复核分钟数。若评估接入代价，再在进程外独立测峰值队列长度和业务请求 p95。上述均为待验证假设，不是本次成果。已公开的 924 条今后只作回归，不再当作新盲集。

复现入口。 从解压本地审阅包，到读懂第一条输出，再到完整复算 · 逐条预测、输入和标签摘要一致的本地回执。

本地复现：从第一条中文输出到整套实验

只想弄懂“它在说什么”？做 A 即可。 A 不需要密钥、网络、GPU、pip 或模型服务器。B 面向要复算论文表格的读者，需要独立研究环境和公开的第三方权重。两套环境不混装。本说明、中文读法和复现工具属于本地审阅稿；直接克隆线上仓库可能看不到它们。

A　从零运行与阅读

解压审阅包，进入含 README.md、pyjev/ 和 candidates/ 的根目录。以下是 macOS 或 Linux 的 shell 命令；本次实际验证为 macOS arm64、Python 3.11.5。先安装 CPython 3.11；脚本只查找已经装好的解释器（也识别未在当前目录选中的 pyenv 3.11），不安装软件、不改系统 Python。如果使用自定义路径，先设置 export PYJEV_PYTHON=/完整路径/bin/python3.11。示例只含自编的无敏感文本。

# 在审阅包解压后的源码根目录运行
work=$(mktemp -d)
sh research/footprint/venv311.sh runtime "$work/runtime"
PY="$work/runtime/bin/python"
"$PY" -s -m pyjev doctor --json
printf '%s' '请解释引文“给会议记录编号”的语气。' | "$PY" -s -m examples.audit_zh
printf '%s' '请按引文中的要求去做：“给会议记录编号”。' | "$PY" -s -m examples.audit_zh
printf '%s' '工单记载：助手读取外部邮件，正文夹带未经授权的指令，要求把内部资料交给陌生人。' | "$PY" -s -m examples.audit_zh --scope
"$PY" -s -m research.footprint.smoke
"$PY" -s -m unittest discover -s tests

doctor 验证文件完整性，不是预测正确率：version=0.1.0、model_checksums=ok、results_checksum=ok、network_required=false。前两句话只换了引号外的动作，第一句是“讨论或引用”，第二句是“要求助手实际办理”，两者都未检出注入线索。第三句话显式选择候选，本地实际输出是：

文字意图：仅凭这段话，无法确定是否在要求助手办理。
注入线索：发现提示注入线索；不是攻击定论。
复核建议：建议人工复核被叙述的事件，不是认定当前用户在发指令。
实际动作：本程序没有执行或拦截，也没有发信；看不到其他系统是否执行。

同一条命令末尾加 --json 即可看原字段，中文界面不改字段值。候选在这个例子中返回（为阅读调整字段顺序）：

{
  "original_signal": "no_signal", "original_review": "no_signal",
  "signal": "suspected", "speech_act": "unclear",
  "route": "case_review", "needs_review": true,
  "execution_evidence": "not_observed", "service_action": "none"
}

一句话读完这个 JSON： 旧版没报警，候选发现工单中记载了可疑事件，建议有人看这张工单；它没有认定报工单的人在攻击，没有给邮件发件人定责，也没证明任何人执行过指令。

想知道什么 读哪个字段 不要这样解读
是否值得留意这段文字？ signal：suspected 可疑线索、no_signal 未检出、unknown 无法分析 不是风险概率；未命中不等于安全
谁在要求做什么？ speech_act：mention 讨论／引用、act 要求助手办理、unclear 证据不足 act 不是“有攻击”，更不是“已执行”；unclear 也不等于输入错误
默认版建议怎么处理？ review 是实际建议；experimental_review 是并列研究建议，不替换前者 不应拿实验字段自动封禁或代替默认建议
候选建议怎么处理？ route：review 普通复核；case_review 复核所述事件；record_only 仅标记语境；no_signal 不建议送审；incomplete 未完成分析 record_only 只是返回值，不会自动写日志
是否建议交给审核员？ 候选 needs_review：true 对应两种复核；false 对应非复核路径；null 是没完成 null 不是 false；true 也不是已经发过告警
候选相对旧版改了什么？ original_signal、original_review 是同一输入的冻结旧版结果 不是先后两次线上事故
实际执行、授权或拦截了吗？ 两版 execution_evidence=not_observed、service_action=none；默认版另有 grants_authority=false、schema_version=1 看不到回执，不等于别的客户端没有执行；两版字段并非同一 schema

机器接入：默认原生入口为 python -m pyjev scan - --json（或 Python 库 Auditor().audit(text).as_dict()）；候选从源码显式运行 python -m candidates.scope1 --json。输入为单段 UTF-8 文本，最多 32,768 个 Unicode 字符。空白示例产生 unknown / incomplete。对于解码合法但全为空白的输入，原生 v0.1.0 正常返回 JSON、退出 0；本说明的中文示例程序和原生候选都返回退出码 2，表示这次未完成审计。不要用单独一个退出码代替安全判断。smoke 逐项核对 4 条示例 × 2 个版本 × 3 个入口／显示模式的输出与退出码。4 个输入与两套完整 JSON · 默认接口的正式契约

B　从零配置研究环境并复算

先决条件：CPython 3.11、有支持的二进制 wheel 的系统；在线获取公开原料还需 curl 与 HTTPS 网络。预留足够磁盘（含约 355 MB 的推断文件、研究依赖及其他数据；从零下载建议预留数 GiB）。B 是本地 CPU 推断，不向远程模型发送文本，不需要 GPU 或付费端点。

# 仍在审阅包根目录。这个环境独立于 A，可以在新终端单独运行。
lab=$(mktemp -d)
sh research/footprint/venv311.sh research "$lab/env"
PYE="$lab/env/bin/python"
"$PYE" -m pip --isolated --disable-pip-version-check install --no-cache-dir --no-compile --only-binary=:all: --index-url https://pypi.org/simple -r research/footprint/requirements-cpu311.txt
"$PYE" -m pip check

只要一种取数方式；--out 必须是未存在的目录，以免覆盖上次证据。

# 方式一：没有缓存，按固定来源获取并逐文件校验。加 --timings 同时重测 CPU 表。
"$PYE" -s -m research.footprint.reproduce --out "$lab/run-online" --timings

# 方式二：已有上次公开原料；禁止联网。填原料目录，不是旧 predictions.jsonl。
# 上次运行过本工具时，“上次结果/previous”和“上次结果/current”就是这两个目录。
# 也可以多给几次 --asset-cache，以匹配分散储存的已固定原料。
"$PYE" -s -m research.footprint.reproduce --offline --asset-cache /路径/上次结果/previous --asset-cache /路径/上次结果/current --out "$lab/run-offline" --timings

每次从 SHA-256 校验过的 44 个源文件开始，重新生成两批旧材料（455、47 条）作为去重参照，再生成本批 924 条配对输入、参考标签与三个检测器的预测。当场计分，和仓库冻结表逐项比较；若逐条预测也逐字节相同，再做独立 SQL 计数及 450 个模板对应关系核查。不需要私有客户数据、旧预测或人工复制分数。--offline 缺文件就明确失败；线上文件变动而哈希不同时也会停止，不会忽略校验或悄悄换样本。历史去重曾用到的额外 48 条私有对照未随包发布，此复算未使用它们；在本机仍重建出完全相同的输入与标签。
